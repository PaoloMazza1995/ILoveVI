# :tools:tilegen

A JVM library + CLI that turns one full-resolution map image into the tile pyramid the app serves,
uploads it to Supabase Storage, and registers it as a new `map_config` row. Used by maintainers
(and, as a library, by `:tools:map-editor` for pin placement) — never shipped in the app itself.

## Rights note

**This tool never downloads, embeds, or re-hosts an official GTA VI map or a fan-made recreation of
one.** `--source` must point at an image the project owns or is otherwise allowed to use. For local
development, generate a clearly-fake placeholder instead:

```sh
./gradlew :tools:tilegen:run --args="generate-placeholder --out placeholder-map.png"
```

This writes an 8192x6144 PNG with a coordinate grid and an unmissable "PLACEHOLDER MAP — NOT GTA
VI — DEV USE ONLY" watermark (`com.pamaz.vi.tools.tilegen.placeholder.PlaceholderMapImage`). Point
`--source` at it for any local run of the real pipeline below.

## Usage

```sh
# Tile a local image, write only to disk (no Supabase access, no credentials needed):
./gradlew :tools:tilegen:run --args="--source ./placeholder-map.png --out ./tiles"

# Tile a remote (HTTPS-only) image, upload it, and register a new map_config row:
export SUPABASE_URL=http://127.0.0.1:54321
export SUPABASE_SERVICE_ROLE_KEY=...   # never commit this; see backend/README.md
./gradlew :tools:tilegen:run --args="--source https://example.com/map.png --out ./tiles --upload"

# Same, but without actually calling Supabase (prints what would happen):
./gradlew :tools:tilegen:run --args="--source ./placeholder-map.png --out ./tiles --upload --dry-run"
```

Flags: `--source <url|path>` and `--out <dir>` are required. `--upload` uploads the generated tiles
to the `map-tiles` bucket and inserts the `map_config` row; `--dry-run` (only meaningful with
`--upload`) does everything except the network calls. `--map-version N` pins the version instead of
auto-deriving it (current max + 1 from `map_config`, or `1` if not uploading). `--tile-size N`
(default 256, must be even), `--background-color RRGGBB` (default a neutral dark gray), and
`--format webp|png` (default `webp` — see "Output format" below) are rarely needed overrides.

Credentials (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`) are read from the environment only, never
from a file in this repo — see `backend/README.md` for how to obtain them locally or for a remote
project.

## What a new map version means for existing pins

`MapPin.mapVersion` records which map image a pin's `NormalizedPoint` was placed on. Generating and
registering a new `map_config` row (a new `map_version`) does **not** move or re-validate any
existing pin — they keep the old `map_version` value, pointing at normalized coordinates that may no
longer line up with the new image. Repositioning them onto the new map is a manual step done later
in the placement tool (`:tools:map-editor`), not something this tool does automatically.

## How tiling stays memory-safe

The real map image can be very large — up to 32768px per side (`MapPublishPlanning.MAX_DIMENSION_PX`
in `:tools:map-editor`; the placeholder is 8192x6144, the eventual real one isn't known yet). Even
at that ceiling, this tool never decodes the whole image into memory:

1. The top (`maxZoom`, 1:1) level is generated by streaming the source image one horizontal,
   tile-row-tall strip at a time (`ImageReadParam.sourceRegion`) — peak memory is one strip plus one
   tile (at the 32768px ceiling and the default 256px tile size, one strip is ~33MB decoded, not
   hundreds of MB for the whole image).
2. Every lower zoom level is built from the 4 child tiles just written at the level above (halved
   and composited) — the standard tile-pyramid technique. The source image is never reopened; at
   most 4 child tiles + 1 output tile are in memory at once.

Partial tiles at the image's right/bottom edge are padded with `--background-color`.

The native max zoom is derived purely from the source image's own size (`2^z * 256 >= the long
side`): 4096px → 4, 8192px → 5, 16384px → 6, 32768px → 7 (`TileScheme.maxZoom`, `:core:model`).
Total tile counts across every level, 0 through that max, follow the same geometric series: 341,
1365, 5461, 21845 tiles respectively.

## Output format

Tiles are written as **WebP, lossy, quality ~82** by default (`TileFormat.WEBP`,
`WEBP_LOSSY_QUALITY`) — the map is always fully opaque (no tile ever needs transparency), and lossy
WebP at this quality is several times smaller than PNG for a visually equivalent result, which
matters directly against Supabase Storage's per-plan quota (see `:tools:map-editor`'s
`SupabaseStorageLimits`). **PNG remains available as a fallback** (`--format png` /
`TileFormat.PNG`) in case a future client target can't decode WebP — decode support was verified,
not assumed, before defaulting to WebP: Android's `BitmapFactory` has decoded WebP natively since
API 14/18 (well under this app's `minSdk`), and Compose Multiplatform's Skia-backed image decoding
(`:core:mapview`'s `decodeImageBitmapDownscaled`, used on both the JVM/desktop and iOS targets)
documents WebP as a supported input format. No target currently needs the PNG fallback.

The chosen format's extension is baked into `tile_url_template` (`.../{z}/{x}/{y}.webp` by
default) — a client never needs to guess or be told the format separately; it just follows the
template. The actual encoder is `com.luciad.imageio.webp.WebPWriter` (a `javax.imageio`
`ImageWriter` plugin, since the JDK's own `javax.imageio` has no built-in WebP encoder).

Uploads use a long, immutable cache header (`Cache-Control: max-age=31536000, immutable` — see
`:tools:map-editor`'s `SupabaseRemoteTileStorage`): every map version gets its own storage folder,
so a given tile URL's bytes never change after it's first uploaded, and clients never need to
revalidate a cache hit (`:core:mapview`'s own `TileDiskCache` relies on exactly this).

## Library API

Everything the CLI does is also a plain suspend-function API, for `:tools:map-editor` to call
in-process instead of shelling out:

- `TileGenPipeline.run(request: TileGenRequest, httpClient: HttpClient): TileGenResult` — the whole
  pipeline (fetch → tile → upload → register).
- `TilePyramidGenerator.generate(...)`, `SourceImageFetcher.fetch(...)`,
  `SupabaseAdminClient.{nextMapVersion,uploadTiles,insertMapConfig}(...)` — the individual steps,
  for callers that only need part of the pipeline (e.g. tiling an already-local image with no
  Supabase access at all).

## Tests

`src/test` covers tile count/dimensions per zoom level and top-level stitching against a synthetic
1000x700 image (no network), CLI argument parsing/validation (incl. `--format`), the WebP/PNG
round-trip through the real `WebPWriter`/`ImageIO` codecs (`TilePyramidGeneratorTest`'s
`generate_webpDefault_roundTripsThroughRealCodec`) and format-extension mapping (`TileFormatTest`),
and the Supabase request shape (headers, snake_case body, dry-run short-circuiting) against a mocked
Ktor engine — no real network or Supabase stack needed to run `./gradlew :tools:tilegen:test`.
Tile-count/native-zoom math for the 4096/8192/16384/32768px sizes is tested where the number is
actually consumed, `:tools:map-editor`'s `MapPublishPlanningTest` (both modules share the same
`TileScheme` from `:core:model`, so there's one source of truth for the formula, not two tests
duplicating it in two modules).
